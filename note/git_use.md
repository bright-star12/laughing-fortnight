# Git 与 VS Code 使用学习记录

## 一、学习背景

通过观看 B 站教学视频并与 AI 讨论，我逐渐理解了 Git 的基本使用流程，并尝试在 VS Code 中完成文件编辑、本地提交和远程同步。

Git 用于记录和管理版本，GitHub 用于托管远程仓库，VS Code 则提供图形界面，方便查看改动并执行相关操作。

## 二、打开仓库并编辑文件

我将包含 `.git` 目录的项目文件夹拖入 VS Code，随后新建了一个 `.py` 文件，编写几行代码并保存。

这里应打开项目目录，而不是单独打开 `.git` 目录。保存文件只会更新工作区中的内容，不会自动创建 Git 提交，也不会将改动上传到 GitHub。

## 三、暂存与本地提交

在 VS Code 的“源代码管理”面板中，我查看文件改动，将需要记录的文件暂存，并填写提交说明后执行提交。

这一过程对应以下 Git 操作：

```bash
git add <文件路径>
git commit -m "说明本次改动"
```

`<文件路径>` 应替换为实际路径。暂存决定哪些改动进入本次提交；提交则将这些改动记录为本地仓库中的一个版本。每次提交都发生在本地，之后仍需推送才能上传到远程仓库。

在我的操作过程中，未填写提交说明时，VS Code 打开了提交信息编辑窗口。我在其中补充说明后完成提交；具体界面可能随设置而有所不同。

## 四、拉取、推送与同步

提交完成后，我使用了 VS Code 中的“同步更改”按钮。为理解这一操作，我进一步梳理了几个命令之间的区别：

| 操作 | 作用 |
| --- | --- |
| `git fetch` | 获取远程提交并更新远程跟踪分支，不直接整合到当前工作分支 |
| `git pull` | 先获取远程更新，再根据配置整合到当前分支 |
| `git push` | 将本地提交推送到远程仓库 |
| VS Code“同步更改” | 先拉取，再推送 |

`git pull` 的整合方式可能是合并（merge）或变基（rebase），取决于配置和命令选项，因此不能在所有情况下都简单理解为 `git fetch + git merge`。

## 五、对合并冲突的初步理解

当时我主要使用个人仓库，尚未完整测试本地和远程分别修改同一文件时的处理流程。

目前的理解是：本地与远程内容不同，并不一定产生冲突。Git 可以自动整合许多互不重叠的修改；当修改无法自动协调时，才需要手动处理。文本冲突通常会在文件中显示冲突标记，VS Code 也可以提供相应的处理界面。

处理冲突时，需要比较双方修改，整理出最终内容，而不是直接删除其中一份。解决后还应检查文件，并根据当前进行的是合并还是变基，完成相应的后续操作。

## 六、克隆老师的课程仓库

为了查看课件和相关资料，我将老师提供的仓库克隆到了桌面，方便后续查阅。操作方式是在目标目录执行：

```bash
git clone <老师提供的仓库地址>
```

克隆得到的是本地副本，并不意味着自动获得向老师仓库推送修改的权限。

## 七、实践收获与后续计划

这次实践让我逐步理解了“编辑并保存 → 暂存 → 提交 → 推送”的基本流程，也意识到本地提交和远程上传是两个不同的步骤。遇到问题时，我通过与 AI 反复讨论、核对实际操作，最终完成了这次提交与同步。

后续我准备继续学习分支操作，并在测试仓库中练习以下场景：

1. 本地与远程分别产生新提交时的整合。
2. 同一文件的不同位置和相同位置被修改时的处理差异。
3. 查看提交历史、比较版本和撤销改动。

后续使用中遇到的新问题和解决方法，将继续补充到这份记录中。
